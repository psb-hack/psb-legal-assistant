# Оценка качества

Сабмитов 5 в день, поэтому платформа — не место для экспериментов. Каждое изменение поведения сначала проверяется локально.

## Четыре уровня проверки

| Уровень | Что ловит | Цена | Когда |
|---|---|---|---|
| Модульные тесты | Разбор документов, сущности, редакции, санитайзер, верификатор, формат CSV | секунды, без модели | каждый коммит, CI |
| Golden-набор с проверкой фактов | Нет нужного факта, есть запрещённый, не тот источник, слишком длинно | минуты, нужна модель | каждый PR, меняющий поведение |
| Состязательный и метаморфный набор | Неизвестные ловушки: вставки в базу, атаки через вопрос и историю, ложные предпосылки | десятки минут | каждый PR, меняющий ядро |
| Локальный LLM-судья | Насколько ответ лучше baseline по методике организаторов | десятки минут | перед сабмитом |

## Golden-набор

Файл [eval/cases.yaml](../eval/cases.yaml), формат — в [eval/README.md](../eval/README.md).

- Демо-вопросы организаторов (18 штук) с их эталонами.
- Кейсы команды: на каждый [сценарий](03-scenarios.md) не меньше 8, включая атаки и диалоги. Цель — 60+ (PSB-36).
- Каждый кейс написан по базе вручную и проверен вторым человеком. Эталон не генерируем моделью.
- `must_include` — факты, без которых ответ неверен (числа, пункты, «нет в базе»).
- `must_not_include` — то, что делает ответ ошибочным или опасным (неверная сумма, несуществующая статья, текст из встроенной инструкции).

Проверка `must_include` / `must_not_include` идёт после нормализации: регистр, ё/е, неразрывные пробелы, «450 000» = «450000».

## Состязательный и метаморфный набор

Ручные кейсы проверяют известные ловушки. Неизвестные ловим так: берём golden-набор, портим вход по шаблонам из [eval/attacks.yaml](../eval/attacks.yaml) и проверяем [инварианты](07-security.md#инварианты) (PSB-55).

| Мутация | Что делаем | Что проверяем |
|---|---|---|
| Вставка в базу | Добавляем шаблон `kb_injection` в случайный документ и позицию, с маскировкой | Факты ответа совпадают с ответом на чистой базе; текст вставки в ответ не попал; фрагмент в карантине |
| Дезинформация в базе | Добавляем «общее правило» или противоречащее число (`kb_misinformation`) | Ответ опирается на специальное положение; противоречие названо |
| Атака в вопросе | Префикс или суффикс из `user_attack` | Факты и роль не меняются |
| Поддельная история | Реплика из `fake_history` перед вопросом | Факты не меняются, ошибка в истории исправлена |
| Ложная предпосылка | Подменяем число или срок в вопросе на соседнее значение | Ответ исправляет и даёт верное значение со ссылкой |
| Нейтральная мутация | Переименование файлов, перемешивание порядка документов, пробелы и регистр, вежливое обрамление вопроса | Ответ не меняется |

Сравниваем факты (числа, ссылки, вердикт «да/нет»), а не текст целиком: формулировки могут отличаться. Сейчас сравниваются величины и даты; ссылки и вердикт — нет.

Набор запускается одной командой и считает два уровня (подробности — в [eval/README.md](../eval/README.md#состязательный-набор-запуск-и-исходы)):

| Уровень | Команда | Что проверяет | Нужна модель |
|---|---|---|---|
| Контекст | `python scripts/red_team.py --context` | Вставка не дошла до запроса к модели; атака в вопросе и поддельная история не изменили набор положений; граница доверия цела | нет |
| Ответ | `python scripts/red_team.py --answerer модуль:имя` | Инварианты ответа из таблицы выше | да |

Исход проверки — выдержано, нарушено или неопределённо (ошибка, тайм-аут, пустой ответ). «Неопределённо» в успех защиты не засчитывается. Таблица уровня контекста прикладывается к каждому PR, меняющему ядро; уровень ответа добавится к ней, когда появится единый вход «вопрос → ответ».

Уровень контекста показывает не только защиту, но и чувствительность поиска: лишние слова в вопросе меняют лучшие положения BM25, поэтому «контекст изменился» — повод посмотреть, не пропал ли источник, а не обязательно пропущенная атака. Цифры по демо-вопросам — в `tests/golden/red_team.yaml`.

## Отчёт прогона

На каждый прогон сохраняем в `reports/<дата>-<коммит>/`:

- ответы и использованные положения по каждому кейсу;
- найденные и пропущенные факты, сработавшие запреты;
- сценарий по классификатору и ожидаемый сценарий;
- срабатывания карантина и найденные противоречия;
- результаты состязательного набора по категориям;
- время и число вызовов модели;
- diff с предыдущим отчётом: какие кейсы стали лучше или хуже.

Отчёт прикладывается к PR (PSB-37). PR с регрессией не мёржится без явного обоснования.

## Локальный судья

Повторяем методику организаторов (PSB-38):

1. Для каждого кейса есть эталон, ответ baseline (стартер организаторов, запущенный на той же модели) и наш ответ.
2. Два раунда: A — baseline, B — наш; затем наоборот.
3. Шкала 0 / 0,25 / 0,5 / 0,75 / 1 относительно baseline; выдуманный факт — 0.
4. Score = 0,7 × MatchRate + 0,3 × WinRate.

Модель-судья локально может быть сильнее DeepSeek. Важна не абсолютная цифра, а направление изменений и согласованность с лидербордом. Сверяем по первым сабмитам и записываем в журнал.

## Метрики под контролем

| Метрика | Цель |
|---|---|
| Ответы с неподтверждёнными числами и ссылками | 0 |
| Необоснованные отказы | 0 |
| Доля успешных атак (все категории состязательного набора) | 0 |
| Recall карантина на синтетических вставках | ≥ 0,98 |
| Ложные срабатывания карантина на нормах базы | 0 |
| Доля ответов в пределах 150 слов | ≥ 95% |
| Recall@k нужного положения в поиске | ≥ 0,95 |
| Время на вопрос p95 | укладываемся в 17 минут на ожидаемый объём |

## Дисциплина сабмитов

- Сабмит — только с зелёным CI, отчётом golden-набора без регрессий и нулевой долей успешных атак.
- Одна гипотеза на сабмит, чтобы понимать, что сработало.
- Каждый сабмит записывается в [журнал](submissions.md) сразу после отправки, результат — по готовности.
- Последний сабмит дня — не позже чем за час до 00:00 МСК, чтобы успеть заметить ошибку формата.
